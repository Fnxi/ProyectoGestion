\section{Introduccion}
El desarrollo de software moderno no concluye cuando una aplicacion funciona en la computadora del programador. Una API que se entrega a usuarios requiere controles de calidad repetibles, una forma confiable de empaquetar sus dependencias y un mecanismo seguro para llegar al servidor donde sera consumida. La integracion continua y la entrega continua, conocidas como CI/CD, responden a esta necesidad al automatizar las verificaciones y el despliegue desde un cambio versionado hasta una version disponible en produccion.

Este proyecto implementa ese flujo para una API REST de tareas y categorias desarrollada con ASP.NET Core y SQLite. La aplicacion ofrece operaciones para administrar tareas, categorias, respaldos y estado de salud. Cada cambio dirigido a la rama principal inicia GitHub Actions: el servicio se prueba de forma aislada, se mide la cobertura de codigo y, si se cumplen las condiciones de calidad, se construye una imagen Docker. La imagen se publica en Docker Hub con una etiqueta inmutable basada en el SHA del commit, lo que permite identificar exactamente el codigo que se esta ejecutando en cada despliegue.

La etapa de entrega se ejecuta en una instancia Ubuntu de Amazon EC2. Un script recibido por SSH descarga la imagen validada, inicia una version candidata en un puerto local alterno y consulta el endpoint de salud. Nginx cambia el trafico HTTP hacia esa version solo despues de comprobar que responde correctamente. Este patron blue/green reduce la interrupcion visible para los consumidores de la API y conserva los datos en un volumen Docker separado de los contenedores. Las credenciales de Docker Hub, la direccion del servidor y la clave privada no se almacenan en el repositorio; GitHub Secrets las inyecta exclusivamente durante la ejecucion autorizada.

El resultado demuestra que automatizar no significa omitir controles, sino convertirlos en condiciones obligatorias y auditables. La evidencia de pruebas, cobertura, etiquetas de imagen y ejecuciones del workflow permite reconstruir el recorrido de cada entrega. A su vez, la separacion entre codigo, configuracion sensible y datos persistentes favorece una operacion mas segura y facilita que el equipo pueda repetir el proceso sin pasos manuales ambiguos.

El workflow ejecuta Jest, que inicia la API con una base SQLite temporal para realizar pruebas de integracion. \texttt{dotnet-coverage} recolecta la cobertura del proceso ASP.NET y el pipeline exige al menos 70\% de cobertura de lineas. Luego Docker construye una imagen multi-stage: la etapa SDK compila y publica, mientras la imagen final contiene solo el runtime necesario.

Para el despliegue, el script determina cual de los puertos locales 8081 o 8082 esta activo. Descarga la imagen identificada por SHA, inicia el contenedor alterno, prueba \texttt{/api/health} y recarga Nginx. Finalmente elimina el contenedor anterior. La base SQLite reside en el volumen \texttt{webapp-api-data}, por lo que no se pierde al recrear contenedores.

\section{Conclusion}
La implementacion integra desarrollo, pruebas, empaquetado y despliegue en un unico proceso repetible. La ejecucion automatica de pruebas de integracion y el umbral de cobertura convierten la calidad en una condicion previa a la entrega. Docker elimina diferencias entre el entorno local y la instancia EC2, mientras que las etiquetas con SHA permiten identificar con precision la version desplegada.

El despliegue blue/green propuesto disminuye el riesgo de indisponibilidad al validar la version candidata antes de redirigir el trafico. El uso de GitHub Secrets y la verificacion de la clave de host SSH evita exponer credenciales, direcciones o claves en el codigo fuente. Como mejora futura, la API puede ampliar su dominio hasta el numero de endpoints requerido por la rubrica y migrar SQLite a un servicio administrado si aumenta la concurrencia o la necesidad de escalabilidad.
